А как же остальные нативы на примитивах?

2026-11-23

HashMap и сортировки Rust на том же входе, что Go, Bun, C и C++. Цена хешера, резерва и стабильности.

После статей об устройстве хеш-таблиц, замерах Go и JavaScript и сортировках остался вопрос про Rust. Я добавил его в оба стенда и повторил контрольные замеры на Mac mini M4 Pro. В первой части сравниваю хеш-таблицы на целых и строковых ключах. Во второй - сортировки на массивах i32, от случайного порядка до почти готового.

Хеш-таблицы

В HashMap хешер вычисляет число из ключа, а таблица выбирает слот. Rust позволяет поменять хешер и оставить тот же HashMap. Я использовал это, чтобы сравнить два варианта на одних и тех же целых ключах.

Что делает get

В стандартной библиотеке Rust HashMap использует Swiss Table из hashbrown. Хеш задаёт стартовую позицию и семибитную метку H2. Таблица читает группу компактных меток и проверяет Eq только для слотов с подходящей H2. Если ни один ключ не подошёл, пустой слот завершает поиск. При отсутствии пустых слотов поиск переходит к следующей группе. Маркер удаления разрешает продолжить поиск. Документация HashMap · Схема поиска Swiss Table

Rust 1.98 использует hashbrown 0.17.1. На Apple Silicon его ветка NEON читает восемь меток за раз. На x86 с SSE2 группа шире - 16 меток. Зависимости стандартной библиотеки · Выбор реализации группы · Группа NEON

Смысл H2 в том, чтобы меньше читать сами ключи. При равномерных метках произвольный занятый слот проходит фильтр примерно в одном случае из 128. Если у ключей одинаковые H2, этот фильтр перестаёт экономить сравнения внутри группы.

Для пользовательских ключей Eq и Hash обязаны согласоваться. Если два ключа равны, их хеши должны совпадать. При совпадении хешей разных ключей окончательное решение принимает Eq. Контракт Hash

Что меняется при смене хешера

Хешер по умолчанию в Rust 1.98 - SipHash 1-3 со случайным начальным состоянием RandomState. Он затрудняет подбор коллизий, когда ключи приходят извне. API BuildHasher позволяет выбрать другой хешер для отдельной карты. Документация HashMap

В контрольном варианте для u32 хеш равен самому ключу. Это убирает вычисление SipHash и одновременно меняет раскладку таблицы. Здесь hashbrown берёт H2 из семи старших битов 64-битного хеша, а начальный слот выбирает по младшим битам. Ключи занимают 31 бит, поэтому H2 у всех записей равен нулю. Разница между вариантами включает и вычисление хеша, и раскладку. Этот контрольный хешер теряет защиту от подбора коллизий. Метка H2 · Старт пробирования

Вставка, удаление и запас места

HashMap::with_capacity(n) заранее выделяет место как минимум для n элементов. Это позволяет пройти известный объём без промежуточных расширений. За слишком щедрый резерв приходится платить памятью и временем обхода. iter() сканирует метаданные, включая пустые слоты, поэтому обход занимает O(capacity). Резерв и обход в HashMap

После серии удалений полезно сравнить len() и capacity(). Таблица сама не сжимается. shrink_to_fit() сокращает запас настолько, насколько позволяет раскладка таблицы. shrink_to(n) задаёт нижнюю границу, а clear() сохраняет память для повторного заполнения. BTreeMap подходит для обхода по возрастанию ключей и запросов range. Управление ёмкостью HashMap · Документация BTreeMap

Сравнение с Go, Bun, C и C++

Рядом с Rust 1.98.0 я запустил Go 1.27.1, Bun 1.4.3, C uthash 2.3.0 и std::unordered_map из libc++ 220106. C и C++ собрал Apple Clang 21. Все тайминги сняты на Mac mini M4 Pro с macOS 27.0.1 в режиме Automatic.

Таблицы содержат медианы семи повторов в нс на операцию. Генератор mulberry32 с seed 42 выдаёт миллион ключей и отдельный миллион для промахов. Строки имеют вид key-%010d. Ключи подготовлены заранее. Вставка начинается с пустой таблицы без резерва. Поиск, обход и удаление начинаются с заполненной таблицы. Смешанный поток состоит из 50% чтений, 30% записей и 20% удалений.

Порядок смешанных операций совпадает, но Rust, C и C++ читают команды в упакованном виде. В цифры входит стоимость контейнера, хешера, представления ключа и обвязки.

Сортировки

В стандартной библиотеке Rust sort() сохраняет порядок элементов с равными ключами. sort_unstable() не даёт такой гарантии и обходится без выделения рабочей памяти в куче. В списке событий, уже отсортированном по времени, стабильная сортировка по пользователю сохранит хронологию событий каждого пользователя. В массиве i32 равные значения неразличимы. Такой вход позволяет сравнить время работы двух алгоритмов при разном порядке и числе значений.

За вызовами стоят два алгоритма

sort_unstable() в Rust 1.98 основан на ipnsort. Обычно он разбивает массив по опорному элементу, как quicksort. Если разбиения идут плохо, heapsort ограничивает время в худшем случае величиной O(n log n). На полностью отсортированном входе и на строго обратном порядке достаточно линейной работы. Документация sort_unstable · Исходник Rust 1.98

sort() основан на driftsort. Он сочетает стабильное разбиение со слиянием и использует уже отсортированные участки. Полностью отсортированный и строго убывающий вход он тоже обрабатывает за линейное время. На миллионе i32 эта реализация запрашивает рабочий буфер на миллион элементов, то есть 4 МБ. Коротким срезам хватает памяти на стеке. Размер буфера следует из исходника. Документация sort · Исходник Rust 1.98

Оба алгоритма используют повторяющиеся значения. Для k различных ключей документация даёт ожидаемую сложность порядка n log k при k больше одного. Поэтому на миллионе элементов из тысячи значений алгоритм может сделать меньше работы, чем на миллионе почти уникальных ключей. Сложность сортировок Rust

Замеры сортировок на миллионе i32

Все сортировки получили одни и те же файлы из генератора sort-bench. random хранит исходную последовательность, sorted - её в порядке возрастания, reverse - в обратном порядке. В nearly генератор меняет местами тысячу пар в отсортированном массиве. В few значения лежат в диапазоне от 0 до 999.

Перед каждой сортировкой стенд восстанавливает исходный массив. Копирование и проверка упорядоченности вынесены за пределы таймера. После прогрева в 300 мс стенд собирает семь серий с целевой длительностью 200 мс. В таблице - медиана в нс на элемент.

Почему обратный порядок оказался дорогим

В reverse я нашёл 385 соседних пар равных значений. Rust распознаёт убывающий участок только при строгом убывании. Стабильная сортировка не может просто развернуть участок с равными элементами, потому что это изменит их взаимный порядок. Когда я подал строго убывающий ряд от 1 000 000 до 1, обе сортировки уложились в 1.7 нс на элемент. Поиск упорядоченного участка в Rust 1.98

Порядок запуска версий чередовался между конфигурациями. Для сравнения версий использую эти парные прогоны. Их абсолютные результаты заметно расходятся с предыдущей серией.

В стандартной библиотеке обеих версий используется hashbrown 0.17.1. Обе документируют SipHash 1-3 как хешер по умолчанию. Вместе с Rust обновился LLVM с 22.1.8 до 23.1.5. Вывод

HashMap Rust показал лучшие медианы в обеих таблицах. На целых ключах попадание заняло 13.2 нс против 17.6 у Bun и 23.1 у C++. В смешанном потоке Rust обошёл ближайший Go примерно в 3.6 раза. На строковых попаданиях Rust, Go и uthash разделили меньше 2 нс. На промахах Rust потратил 12.2 нс против 33.5 у Go и 44.5 у C++.

В сортировках лидер менялся вместе со входом. На случайном миллионе i32 Rust sort_unstable() и C++ std::stable_sort уложились в 52-54 нс на элемент. На почти отсортированном массиве C++ std::sort был в 2.7 раза быстрее лучшего результата Rust. На обратном массиве с дубликатами Go занял 2.8 нс на элемент, Rust sort() - 27.4 нс.

В парном прогоне Rust 1.100.0 снизил медиану попаданий по u32. Время сортировки случайных i32 изменилось меньше чем на 1%. С C++, Go и Bun я сравнивал Rust 1.98.0. В парном прогоне участвовали только две версии Rust.
